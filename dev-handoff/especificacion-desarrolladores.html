Especificación técnica — Gimadd Mentor (prototipo HTML)

Documento para el equipo de desarrollo de la aplicación móvil / web. Describe la lógica funcional y de datos del archivo demo gimadd-mentor-jugador-app.html, con mapa mental, ejemplos y capturas obtenidas del propio prototipo.

PDF: En Chrome o Edge: Archivo → Imprimir → Guardar como PDF. O ejecutar desde la carpeta dev-handoff: ./generar-pdf.sh

1. Mapa mental de la lógica

Visión global: una sola página (SPA) con cinco vistas principales, dos almacenes lógicos (objetivos y partidos), sincronización entre pestañas y exportación del HTML con datos incrustados.

2. Vistas de la aplicación (navegación)

La función showView(name) activa la sección con data-view igual a name (clase is-active) y ajusta la clase del body. Para documentación y capturas, el prototipo admite carga inicial con hash: #jugador, #objetivos, #entrenador, #diario (sin hash = inicio).

3. Modelo de datos — Objetivos

localStorage: clave gimadd_objetivos_v1 (array JSON). Clave de versión embebida: gimadd_objetivos_v1_fileId comparada con gimadd-store-meta.fileId en el HTML: si cambia, se reinicializa desde el JSON embebido gimadd-objetivos-seed (útil al importar un backup).

3.2 Clasificación splitGoals

  • pend (Pendiente de revisión): estado === "pendiente_revision".
  • plan (Plan de acción en proceso): activo y enPlanAccion verdadero.
  • act (Activos fuera del plan): activo y sin plan.
  • done (Completados): estado === "completado".

Pestaña «Plan de acción» (jugador y coach): muestra en orden las secciones pend + plan; el número entre paréntesis en la pestaña es pend.length + plan.length.

4. Modelo de datos — Partidos (diario)

localStorage: gimadd_partidos_v1, con gimadd_partidos_v1_fileId alineado a gimadd-diario-meta. Array de partidos; cada uno puede incluir planAccion: lista de ítems ligada a objetivos por objetivoId.

4.1 Ejemplo de ítem planAccion en un partido

{
  "objetivoId": "g-1777482161796-7qk73oj",
  "titulo": "mejorar saque",
  "practicado": true,
  "sensaciones": "he metido un montón de puntos de saque"
}

4.2 Transición automática a revisión

Para cada objetivo activo con plan, se cuenta cuántos partidos tienen al menos un ítem de planAccion con ese objetivoId y practicado: true, restando practicasUmbralOffset. Si el total ≥ partidosMeta, recalcGoalsFromMatches() pasa el objetivo a pendiente_revision, reinicia la bandera de vídeo y guarda.

5. Sincronización y guardado

  • Evento storage: otras pestañas del mismo origen recargan objetivos o partidos y refrescan UI.
  • BroadcastChannel gimadd_objetivos_channel y gimadd_partidos_channel: aviso inmediato; en el mismo documento el canal también recibe el mensaje, por eso saveGoals durante render() usa { broadcast: false } para evitar un bucle infinito.
  • refreshAllGoalUI(): bandera central tras cambios: banner inicio, listas jugador, espejo coach, dashboard revisión, tabla partidos coach, sección plan en formulario diario.
Implementación nativa: reemplazar localStorage/BroadcastChannel por API + base de datos y mecanismo push o tiempo real acordado; conservar los mismos contratos de datos facilita la migración desde este prototipo.

6. Flujos de interacción (ejemplos)

6.1 Jugador crea objetivo y lo pone en plan

  1. Pulsa FAB «+» en vista objetivos; modal con título, fecha opcional, tipo, número de sesiones meta, checkbox plan de acción.
  2. goalForm.onsubmit crea o actualiza el elemento en el array y llama saveGoals + refreshAllGoalUI.
  3. El objetivo aparece en la pestaña Plan de acción (sección «en proceso») si está activo y marcado en plan.

6.2 Jugador registra partido con práctica de objetivo

  1. En diario, «Agregar resultado partido»; el formulario ofrece objetivos activos en plan para marcar prácticas y sensaciones.
  2. Al guardar, persistMatches + recalcGoalsFromMatches; si se alcanza el umbral, el objetivo pasa a «Pendiente de revisión» y el banner de aviso puede mostrarse en el hub jugador.

6.3 Entrenador completa o reactiva

  1. En dashboard de tarjetas o en el espejo de objetivos, acciones «Marcar completado» / «Reactivar con nuevo %».
  2. Los sliders de progreso en tarjetas tipo espejo actualizan progreso en caliente.

6.4 Exportación downloadFullApp()

Genera un nuevo archivo HTML sustituyendo los bloques JSON incrustados por los datos vivos y nuevos fileId para objetivos y diario, de modo que al abrir el archivo en otro sitio no se mezclen entradas antiguas de localStorage.
